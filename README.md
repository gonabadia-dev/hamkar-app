# هم‌کار — MVP گزارش فعالیت روزانه

اسکلت Full-stack فارسی و راست‌به‌چپ با React، Vite، TypeScript و Supabase Auth/Postgres/Storage، RLS و Edge Functions. این مخزن **کد آماده راه‌اندازی است، نه سرویس مستقرشده**. بهره‌برداری واقعی نیازمند پروژه و حساب‌های متعلق به شما در Supabase و OpenAI، نگهداری محرمانه کلیدها، و دامنه/میزبانی است.

## پیش‌نیاز و راه‌اندازی محلی

1. Node.js نسخه 20 یا بالاتر و npm را نصب کنید. یک پروژه Supabase بسازید و از Project Settings، Project URL و کلید `anon` را بردارید.
2. در پوشه پروژه:

```sh
cp .env.example .env
# .env را ویرایش و VITE_SUPABASE_URL و VITE_SUPABASE_ANON_KEY را مقداردهی کنید
npm install
npm run dev
```

کلید `anon` عمومیِ پروژه است؛ هرگز `service_role` یا `OPENAI_API_KEY` را در مرورگر، Git یا فایل VITE قرار ندهید. `.env` در gitignore است.

## دیتابیس و Storage

Supabase CLI را نصب و ورود کنید. از پوشه پروژه:

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

این migration در `supabase/migrations/001_initial.sql` هشت جدول، شاخص‌ها، RLS و باکت خصوصی `report-audio` (حداکثر ۲۵ MiB) و پالیسی‌های مسیر ذخیره‌سازی را ایجاد می‌کند. فایل SQL را نیز می‌توانید از SQL Editor اجرا کنید، اما روش CLI برای مهاجرت نسخه‌بندی‌شده توصیه می‌شود. پس از اعمال، در Storage مطمئن شوید bucket خصوصی است. مسیر فایل باید `organization_uuid/user_uuid/report_uuid/filename` باشد.

RLS اجازه دسترسی مستقیم مدیر را فقط به گزارش‌های گزارشگران مستقیم همان سازمان می‌دهد؛ RPC آمار تیم فقط تعداد/میانگین را برمی‌گرداند. نقطه‌نظر امنیتی امتیاز پایه از چهار عامل توضیح‌پذیر کیفیت ۳۵٪، اثر ۳۰٪، تکمیل ۲۰٪ و به‌موقع‌بودن ۱۵٪ ساخته می‌شود، نه تعداد کارها. امتیاز AI صرفاً پیشنهادی است و مدیر امتیاز نهایی را جدا ذخیره می‌کند. نقاط قوت/چالش فقط برای خود کارمند قابل‌خواندن‌اند؛ متن رونویسی و صوت برای مدیر مستقیم قابل دسترسی‌اند.

## مهاجرت ۰۰۶ — رفع «فعالیت‌های آینده» و «فعالیت همکاران»

این نسخه دو مشکل را رفع می‌کند:

1. **فعالیت‌های آینده کارمند نمایش داده نمی‌شد:** ستون `status` به `manager_tasks` اضافه شد (پیش‌فرض `pending`) و کوئری داشبورد کارمند فقط تکالیف با وضعیت `pending`/`active` و `due_date >= امروز` را می‌گیرد. سیاست‌های RLS این جدول نیز صریحاً بازنویسی شدند: کارمند فقط تکالیف خودش در سازمان خودش و مدیر فقط تکالیفی که خودش برای گزارشگران مستقیم ساخته را می‌بیند (بدون اتکا به نقش سمت کلاینت و بدون افشای بین‌سازمانی).
2. **فعالیت همکاران خالی بود:** تابع `team_activity_overview()` بازنویسی شد تا میانگین و تعداد گزارش همه همکاران همان سازمان را (فقط به‌صورت تجمیعی: نام، تعداد، میانگین) برای کارمند احرازهویت‌شده برگرداند؛ `SECURITY DEFINER` با `search_path = pg_catalog` و بدون هیچ پارامتر ورودی از کلاینت، پس هیچ افشای بین‌سازمانی رخ نمی‌دهد و متن/جزئیات گزارش‌ها هرگز برگردانده نمی‌شود. علاوه بر این، خطاهای RPC و جدول تکالیف دیگر بی‌صدا نادیده گرفته نمی‌شوند و در UI نمایش داده می‌شوند.

### گام‌های استقرار (اجباری برای رفع مشکل)

1. اگر نسخه قبلی را مستقر کرده‌اید، فقط مهاجرت جدید را اعمال کنید:

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

CLI فایل `supabase/migrations/006_future_tasks_team_activity.sql` را در ترتیب نسخه اجرا می‌کند (001 تا 005 idempotent باز اجرا نمی‌شوند اگر قبلاً اعمال شده‌اند).

2. اگر از SQL Editor استفاده می‌کنید، محتوای `supabase/sql_editor/006_future_tasks_team_activity.sql` را کامل و یک‌جا اجرا کنید (روی پروژه تولیدی اول روی staging آزمایش کنید).
3. سپس فرانت را دوباره بسازید و منتشر کنید:

```sh
npm install
npm run build   # شامل tsc -b
```

4. تأیید پس از استقرار:
   - با حساب کارمند وارد شوید: بخش «فعالیت‌های آینده من» باید تکالیف `pending/active` با سررسید امروز و بعد را نشان دهد و خطای کوئری در صورت وجود در UI ظاهر شود.
   - نمودار «فعالیت همکاران» باید نام، تعداد گزارش و میانگین امتیاز سایر همکاران همان سازمان را نشان دهد.
   - با حساب کارمند سازمان دوم تست کنید که داده سازمان اول دیده نمی‌شود (جداسازی tenant).
   - با حساب مدیر بررسی کنید که تکالیف تخصیص‌یافته جدید با وضعیت `pending` ساخته می‌شوند.

نکته: مهاجرت ۰۰۶ بازاجراپذیر (idempotent) است؛ تکالیف موجود به‌صورت خودکار `pending` در نظر گرفته می‌شوند و نیازی به backfill داده نیست.

## Edge Functions و secrets

```sh
supabase functions deploy register-manager
supabase functions deploy create-employee
supabase functions deploy process-audio
supabase functions deploy save-evaluation
supabase secrets set OPENAI_API_KEY=YOUR_OPENAI_API_KEY
```

توابع از secrets محیط Supabase استفاده می‌کنند؛ `SUPABASE_URL`، `SUPABASE_ANON_KEY` و `SUPABASE_SERVICE_ROLE_KEY` توسط محیط Edge Functions فراهم می‌شوند. **هیچ‌گاه** service role را در frontend قرار ندهید. `process-audio` صوت را برای Whisper با زبان فارسی ارسال می‌کند و سپس خلاصه/امتیاز پیشنهادی غیرتنبیهی می‌خواهد. هزینه و محدودیت‌های OpenAI اعمال می‌شوند. اگر سرویس خلاصه‌ساز در دسترس نباشد ممکن است فقط متن رونویسی‌شده برگردد. ورود با ایمیل تأییدشده خودکار در توابع ساخت حساب انجام می‌شود؛ در محیط تولید سیاست تأیید ایمیل و جریان دعوت/بازیابی را متناسب با سازمان تنظیم کنید.

## انتشار رابط کاربری

`npm run build` خروجی `dist/` می‌سازد. برای Vercel یا Netlify، پوشه پروژه را متصل، build command را `npm run build` و output directory را `dist` تنظیم کنید و دو متغیر `VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` را در تنظیمات محیط استقرار ثبت کنید. دامنه مجاز و redirect URL را در Supabase Authentication → URL Configuration مطابق دامنه واقعی تنظیم کنید. HTTPS اجباری است.

## امنیت و محدودیت MVP

- مدیر سازمان را خودثبت‌نام می‌کند؛ مدیر از مسیر امن Edge Function همکار را ایجاد می‌کند. نقش/سازمان/مدیر از ورودی مرورگر پذیرفته نمی‌شود.
- گذرواژه موقت را فقط از کانال امن تحویل دهید؛ این MVP جریان تغییر اجباری گذرواژه، دعوت ایمیلی، بازیابی گذرواژه سفارشی، MFA، مدیریت ترک خدمت، حذف حساب و اعلان را کامل پیاده‌سازی نکرده است. پیش از استفاده سازمانی برای این جریان‌ها فرآیند بسازید.
- رونویسی و گزارش شامل داده کارکنان است. با رضایت و سیاست شفاف کارفرما ضبط کنید؛ فایل صوتی به OpenAI ارسال می‌شود. از ضبط داده حساس خودداری و هدف، مدت نگهداری، دسترسی، حذف و مبنای پردازش را با کارکنان روشن کنید.
- محدودسازی نرخ، اسکن ضدبدافزار، ثبت رویداد ممیزی، سهمیه و نظارت هزینه AI، کنترل فایل و سیاست retention/deletion عملیاتی برای تولید به زیرساخت جداگانه نیاز دارند. خطای یکپارچه‌سازی صوت ممکن است پس از ثبت خود گزارش رخ دهد؛ کاربر آن گزارش را دوباره ارسال نکند.
- قبل از تولید، RLS و سیاست‌های Storage را با کاربران دو سازمان و مدیر غیرمستقیم آزمایش نفوذ کنید؛ در حال حاضر مجوز مدیر فقط گزارش مستقیم را پوشش می‌دهد. جهت رفع ریسک تغییرات SQL در محیط واقعی بازبینی کد الزامی است.

## پشتیبان‌گیری و چک‌لیست تولید

1. در Supabase پشتیبان‌گیری زمان‌بندی‌شده/PITR متناسب با پلن را فعال کنید؛ علاوه بر پایگاه داده، نگهداری و بازیابی Storage را هم طراحی و بازیابی را دوره‌ای آزمایش کنید.
2. کلید OpenAI و service role را فقط در secret manager نگه دارید، دسترسی کارکنان فنی را حداقلی کنید، کلیدها را rotate کنید و هزینه/خطا را پایش کنید.
3. احراز هویت، تأیید ایمیل/بازیابی، MFA مدیر، سیاست رمز، دامنه‌های redirect و CORS را بررسی کنید. CORS توابع نمونه برای سهولت `*` است؛ پیش از انتشار به دامنه‌های واقعی محدودش کنید.
4. HTTPS، CSP و هدرهای امنیتی میزبانی، محدودسازی نرخ، retention و حذف داده، رضایت صوت، ممیزی تغییر ارزیابی و پاسخ‌گویی رخداد را نهایی کنید.
5. مهاجرت را در staging اعمال و آزمون کنید، نسخه‌های وابستگی را بازبینی و build و آزمون‌های RLS/Storage/backup restore را اجرا کنید. اطلاعات این نمونه، مشاوره حقوقی/امنیتی نیست.

## ساختار اصلی

- `src/`: رابط واکنش‌گرا، RTL، فرم‌ها و کلاینت Supabase
- `supabase/migrations/001_initial.sql`: طرح و سیاست‌های پایگاه داده/ذخیره‌سازی
- `supabase/functions/`: چهار تابع Deno و helper مشترک
- `.env.example`: فقط URL و anon key سمت کاربر
